# Repository structure

## Decision

Use a Bun workspace with the supplied `t3-app-template` adapted into
`apps/web`. The web app uses the Next.js App Router and the T3 data boundary:
tRPC over a single App Router route handler, with ZenStack generating the CRUD
surface from `schema.zmodel`.

The first realtime implementation should be a separate Bun process. This keeps
the WebSocket lifecycle and high-frequency messages out of the Next.js request
runtime while leaving room to replace the in-memory room registry later.

Do not add Redis, Yjs, or a separate database package to the first tracer path.
Introduce each behind a small interface only when its slice needs it.

## Workspace tree

```text
real-time-collaborative-whiteboard/
├── apps/
│   ├── web/                         # Next.js app copied from t3-app-template
│   │   ├── public/
│   │   ├── prisma/                  # Generated Prisma schema/client artifacts
│   │   ├── schema.zmodel            # Authoritative ZenStack schema and policies
│   │   └── src/
│   │       ├── app/                 # App Router pages, layout, providers, and tRPC route handler
│   │       ├── components/          # Shared accessible UI primitives
│   │       ├── features/            # Whiteboard capability slices
│   │       │   ├── canvas/           # Scene model, coordinate mapping, renderer
│   │       │   ├── collaboration/   # Connection, room, and presence UI adapters
│   │       │   └── documents/        # Document loading and save UI
│   │       ├── hooks/               # Thin React lifecycle adapters
│   │       ├── lib/                 # Client utilities and environment config
│   │       ├── server/              # tRPC context, ZenStack client, and generated routers
│   │       └── styles/
│   └── realtime/                    # Bun WebSocket process
│       ├── src/
│       │   ├── rooms/               # Room lifecycle and connected clients
│       │   ├── transport/           # WebSocket parsing, validation, broadcasting
│       │   ├── presence/            # Ephemeral cursor state
│       │   └── persistence/         # Save boundary; implementation added later
│       └── package.json
├── packages/
│   └── contracts/                   # Shared Zod schemas, transport types, and CRDT adapter
│       └── src/
├── docs/
│   ├── slices/                      # Detailed design for each implementation slice
│   └── wtc-whiteboard/              # Roadmap, decisions, and engineering guidance
├── package.json                     # Bun workspace root and orchestration scripts
├── bun.lock                         # Workspace lockfile
└── tsconfig.json                    # Shared compiler defaults/references if needed
```

## Workspace boundaries

```text
apps/web ──imports──> packages/contracts ──> Yjs shared-document adapter
apps/realtime ──imports──> packages/contracts ──> Yjs shared-document adapter
apps/realtime ──calls──> persistence boundary ──> PostgreSQL (later)
apps/realtime ──calls──> fan-out boundary ──> Redis (only when multi-node is required)
```

The browser owns interaction/rendering state. The server owns room membership,
authorization decisions, accepted document updates, and persistence. React
components must not parse raw WebSocket payloads or implement document
conflict rules.

## Template and application rules

- Copy the template into `apps/web`; do not copy its `node_modules` or
  `package-lock.json`.
- Convert the root to a Bun workspace and regenerate one `bun.lock`.
- Use the template's UI and TypeScript baseline with the Next.js App Router;
  do not add new Pages Router routes.
- Retain only UI primitives and layout code that the whiteboard uses.
- Remove example employee/dashboard routes and unused demo dependencies during
  the web bootstrap slice.
- Keep the ZenStack schema and enhanced Prisma client in `apps/web` while the
  web app owns the tRPC persistence path. Extract `packages/database` only
  when both apps need the same client or schema boundary.
- Keep server state in TanStack React Query and local UI state in Zustand.
- Keep Zod schemas at runtime boundaries and avoid duplicate validation.
- Use Docker Compose PostgreSQL for local development and verification.
